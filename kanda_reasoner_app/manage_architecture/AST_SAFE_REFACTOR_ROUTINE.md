# AST Safe Refactor Routine

Owner: `Architecture Review -> Large Module AST Split Audit`

Status: internal reusable methodology

Authority: human strategic direction + Web AI architectural reasoning + deterministic verification

## Purpose

This routine accelerates repeated refactoring of Python modules classified as
`RISK REFACTORING` without weakening the AST classifier, Box Logic, shielding,
no-leak boundaries, source identity, public contracts, or human freeze authority.

The reusable infrastructure is subordinate to the existing Large Module AST
Split Audit subtab. It does not create a new visible tab and does not own the
MODULE_TOO_LARGE queue, Planner, Workbench, AQR, or Freeze writer.

## Human and AI responsibilities

The human:

- sets strategic direction and priorities;
- discusses implementation options before code is written;
- confirms the proposal before implementation or installation;
- runs delivered install and validation commands;
- tests real feature behavior and reports results;
- approves or rejects changes to frozen behavior;
- never has to write implementation code.

The AI:

- reads current source, frozen context, and relevant Error Memory;
- researches unfamiliar or uncertain architecture before implementation;
- explains options and trade-offs before coding;
- writes complete source and validators after confirmation;
- delivers self-installing and self-validating governed ZIPs by default;
- diagnoses failures from exact validation output;
- delivers cumulative correction patches when needed;
- prepares specialist handoffs when requested or architecturally necessary.

Deterministic tooling:

- verifies exact source identity;
- maps consumers and public contracts;
- detects supported semantic reflection risks;
- compares explicit behavior probes;
- checks dependency direction and shielding;
- runs fresh AST audits for every touched source module;
- builds manifests, hashes, and governed releases;
- fails closed when required evidence is missing.

## Gate 1 - Ingest and exact identity

Input comes from KPR-06-003 and must contain:

- exact target relative path;
- exact source SHA-256;
- exact source byte length;
- current safety label;
- complete AST audit Markdown;
- complete target source;
- optional preflight evidence generated by this internal infrastructure.

The exact source bytes are authoritative. The routine does not guess another
source version and does not normalize arbitrary whitespace to force a match.

## Gate 2 - Pre-refactor evidence

Before architecture decisions, collect:

- semantic blocker map;
- consumer import records;
- public `__all__` state;
- public functions and class identities;
- signatures and call-shape boundaries;
- defaults and annotations;
- decorator identity and order;
- class bases and dataclass-related decorators;
- current dependency direction;
- active AST audit label and hard blockers.

`__all__` has three states:

- `EXPLICIT_LITERAL`;
- `ABSENT`;
- `UNRESOLVED_DYNAMIC`.

`UNRESOLVED_DYNAMIC` requires AI/human review and must never be silently treated
as equivalent to an absent public surface.

## Gate 3 - Architecture review

The Web AI remains the architectural refactoring authority. Internal services
provide evidence and advisory patterns only.

For nontrivial refactors, compare plausible choices such as:

1. smallest explicit in-place repair;
2. public facade plus evaluation helper;
3. public facade plus invariants helper;
4. public facade plus evaluation and invariants helpers;
5. a domain-specific alternative.

The decision record must state:

- problem;
- forces;
- options considered;
- chosen option;
- rejected options;
- boundary owner;
- dependency direction;
- trade-offs;
- expected file sizes;
- validation obligations.

Known patterns are advisory. Pattern recognition must not automatically authorize
source transformation.

## Gate 4 - Transformation plan and candidate build

Before editing, define a bounded transformation sequence. Typical steps are:

1. preserve the public facade path;
2. add the chosen responsibility owner;
3. move only cohesive behavior;
4. preserve facade delegation and return contracts;
5. replace real blocker behavior explicitly;
6. preserve decorators, annotations, and error contracts;
7. validate behavior equivalence;
8. audit every touched source module;
9. package only after all gates pass.

For multi-prerequisite work, create a prerequisite graph. Do not create one for a
simple repair that does not need it.

## Gate 5 - Behavior characterization

Behavior equivalence uses explicit semantic cases, not random inputs inferred
from signatures.

Reusable scaffold profiles include:

- `CONTRACT_MODULE`;
- `COLLECTOR_MODULE`;
- `PURE_MAPPING_MODULE`;
- `SERIALIZATION_MODULE`;
- `GUI_STATE_MODULE`;
- `CLI_MODULE`;
- `CUSTOM`.

AI reasoning selects meaningful cases. The probe engine executes the same cases
against baseline and candidate implementations and compares:

- normalized return values;
- exception classes;
- exact deterministic exception messages;
- visible side effects represented by the probe;
- ordering where contract-sensitive;
- determinism where applicable.

A structural-only refactor expects zero intentional behavior change unless the
human explicitly approves a separate feature change.

## Gate 6 - Architecture fitness functions

The release must evaluate explicit fitness functions:

- source identity;
- Box ownership;
- no-leak boundary;
- public contract preservation;
- consumer compatibility;
- decorator preservation;
- annotation preservation;
- dependency direction;
- behavior equivalence;
- strict line law;
- semantic reflection risk;
- fresh family AST safety;
- package integrity;
- installability.

These checks operationalize architecture rules that would otherwise exist only
as prose.

## Gate 7 - Fresh touched-family AST audit

Every touched permanent Python source module must receive a fresh AST Split
Audit before release.

For KPR-06-003 success, require:

- `SAFE REFACTORING`;
- zero hard blockers;
- truthful fresh Markdown evidence.

Development-loop caching or incremental checks may accelerate iteration, but
never replace the final fresh touched-family audit.

## Gate 8 - Governed release

The release builder consumes data, not module-specific conditional logic.

The descriptor supplies:

- feature identity;
- payload paths;
- accepted predecessor hashes;
- new hashes;
- focused validator path;
- required markers;
- protected paths;
- do-not-regress rules;
- structural-only behavior-change policy.

The builder prepares:

- `PACKAGE_MANIFEST.json`;
- `INSTALL.ps1`;
- `VALIDATE.ps1`;
- `FREEZE.ps1` for evidence preparation only;
- root-level `KANDA_FREEZE_HINT.json`;
- payload files.

The ZIP is downloaded to the drive root. The install flow stages the ZIP into
`<project>_delete_after_daily_work`, removes the consumed root copy after safe
staging, and never searches Downloads or Desktop as fallback locations.

## Box Logic and shielding law

The AST-safe refactor infrastructure may import only public/shared project
policies and its own Architecture Review services.

Forbidden reach-ins include:

- Large File Refactor Planner internals;
- Workbench internals;
- AQR internals;
- Freeze implementation internals;
- hidden mutable state stored on shared GUI hosts.

The release builder may prepare freeze evidence, but final frozen-memory writes
remain owned by the existing Freeze Feature After Update workflow.

## Strict file-size law

Every permanent file created for this infrastructure or for a refactored source
family must be strictly more than 100 and strictly less than 500 physical lines.

Allowed range: `101-499`.

If a responsibility is too small, merge it with the nearest cohesive owner.

If an owner reaches 500 lines or more, split it across a real logical boundary.

Never add filler, redundant comments, or artificial docstrings merely to reach
101 lines.

## Final governance

The local truth sequence is:

1. governed ZIP delivery;
2. human-approved installation;
3. local validation;
4. human feature testing;
5. correction lane when needed;
6. freeze evidence preparation;
7. `Preview Freeze Entry`;
8. human review;
9. explicit `Confirm and Write`;
10. startup freeze-context refresh.

The human remains the strategic and frozen-behavior authority. The AI remains
responsible for architecture proposals, implementation, validation design, and
complete delivery. Deterministic tools remain evidence and enforcement systems,
not autonomous architecture decision-makers.
