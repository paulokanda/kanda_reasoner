Title:
The Project Reasoner Engineering Handbook
Building Safe, Deterministic, Evidence-Grounded, and Auditable AI Developer Tools

Use this prompt as an additional governance layer for building the Project
Reasoner / kanda_reasoner_app app professionally.

This layer is inspired by Ian Sommerville-style software engineering principles:
requirements engineering, architecture, design and implementation discipline,
testing, software processes, agile and incremental development, dependability,
safety, security, configuration management, software evolution, quality
management, risk management, project planning, and maintainability.

This layer is adapted specifically to Project Reasoner.

Project Reasoner is not just a code search GUI and not just an AI chat wrapper.
It is a deterministic, auditable, evidence-grounded software engineering tool
that helps AI reason safely over Python projects using collected static
evidence, runtime evidence, source excerpts, schema-aware loading, retrieval,
prompt construction, project profiles, and GUI-first workflows.

Every architectural decision must support:

- evidence integrity
- source-truth hierarchy
- project-agnostic behavior
- dynamic PROJECT_ROOT handling
- static/runtime collector separation
- schema compatibility
- retrieval correctness
- prompt-grounding discipline
- AI bridge reliability
- GUI-first usability
- traceability
- maintainability
- controlled evolution

This layer does not replace the existing Reasoner canon.

It is subordinate to:

1. Project Reasoner startup canon.
2. Project Reasoner daily canon workflow.
3. Reasoner box-model canon.
4. Validated frozen Reasoner project canon.
5. Current source files and runtime logs.

It must never override frozen Reasoner behavior.

It must be applied together with the frozen Reasoner rules:

- Keep PROJECT_ROOT dynamic and user-selected.
- Keep the tool project-agnostic.
- Preserve the GUI-first product path.
- Separate static collection from runtime instrumentation.
- Keep AI reading, retrieval, prompt building, and GUI integration in the V10 layer.
- Treat packaging metadata and documentation intent as declared intent, not source truth.
- Treat source code and runtime traces as stronger evidence than documentation.
- Never hide uncertainty in AI answers.
- Never let support tools become second canonical owners of V10 product behavior.
- Use one box per responsibility.
- Deliver one focused bundle per concern.
- Validate before freezing.
- Do not update canon until user validation.

PURPOSE
-------

The purpose of this governance layer is to make Project Reasoner a
professionally engineered AI-assisted developer tool.

Every implementation decision must be treated as professional software
engineering work with explicit requirements, architecture ownership, traceability,
risk control, verification, validation, maintainability, modularity, and
controlled software evolution.

The goal is to prevent:

- accidental complexity
- hidden coupling
- unsafe prompt behavior
- unsupported AI answers
- stale or ambiguous project evidence
- schema drift
- hardcoded target-project assumptions
- static/runtime collector boundary erosion
- duplicate retrieval or prompt logic
- loss of evidence provenance
- invalid confidence claims
- GUI-first workflow bypass
- regression of previously validated behavior
- broad rewrites without ownership
- treating "AI answered" as evidence correctness

Sommerville provides the software engineering discipline.
Project Reasoner provides the evidence-grounded AI developer-tool constraints.
Reasoner requires both.

1. REQUIREMENTS ENGINEERING RULE
--------------------------------

Before implementation, define the requirement.

Every task must state:

- User-visible requirement:
  What should the developer/user be able to do?

- Evidence-safety requirement:
  What must never happen to project evidence, source truth, runtime traces,
  retrieval ranking, prompt construction, schema interpretation, or AI answer
  grounding?

- Functional requirement:
  What specific behavior must the software implement?

- Non-functional requirement:
  What quality must be preserved?
  Examples: reliability, usability, maintainability, auditability,
  portability, Windows/PyCharm compatibility, resolution independence,
  startup stability, schema compatibility, response grounding, and
  project-agnostic behavior.

- Out-of-scope behavior:
  What must not be changed in this bundle?

For Reasoner, evidence-safety requirements are first-class requirements.

A feature is not complete only because the GUI opens or the model returns text.
It must also preserve:

- source-truth hierarchy
- dynamic PROJECT_ROOT behavior
- schema compatibility
- static/runtime layer separation
- retrieval correctness
- prompt evidence boundaries
- failure safety
- traceability
- validation evidence

Each feature should be converted into a testable requirement before coding.

[ENFORCEMENT v1.5.1]
If a requirement cannot be expressed as a testable condition, implementation
must not begin. A requirement stated only as a vague goal such as "improve AI
answers" or "make retrieval better" is not a valid requirement. It must be
decomposed into specific, testable, bounded sub-requirements before any code is
written.

2. EVIDENCE-FIRST REASONER RULE
-------------------------------

Project Reasoner must prioritize evidence integrity over convenience.

The app must support:

- correct source interpretation
- reproducible static collection
- reproducible runtime trace interpretation
- transparent evidence selection
- safe failure behavior
- clear uncertainty handling
- confidence grounded in evidence
- preservation of generated evidence provenance
- distinction between declared intent and implementation truth

The app must never silently guess project architecture or code ownership.

This applies especially to:

- missing project files
- stale generated JSON
- older/deprecated folders
- generated source dumps
- incomplete runtime traces
- missing optional schema sections
- conflicting documentation and source code
- ambiguous package facades
- duplicate public symbols
- unknown project profiles
- failed AI model responses

If the app cannot prove a project fact from evidence, it must say so clearly,
preserve useful partial evidence when appropriate, and guide the user to the
next safe diagnostic step.

Correct answer posture:

- "The source file shows..."
- "The runtime trace indicates..."
- "The documentation claims..."
- "The index suggests..."
- "This is an inference, not directly proven..."

Forbidden answer posture:

- unsupported certainty
- treating documentation as source truth
- treating generated JSON as current source without checking freshness
- treating older/deprecated copies as active code without evidence
- inventing missing files, functions, call paths, or GUI behavior

3. ARCHITECTURE OWNERSHIP RULE
------------------------------

Before editing code, identify the owning architecture box.

Examples:

- Static Data Collector Box:
  owns AST parsing, static evidence harvesting, source indexes, packaging
  metadata, documentation intent, widget registry, import graph, call edges,
  and collector output schema.

- Runtime Collector Box:
  owns runtime instrumentation, trace events, runtime signal connections,
  state snapshots, scenario output, and runtime call-stack evidence.

- Index Loader / Schema Adapter Box:
  owns loading collected JSON, schema compatibility, optional section defaults,
  and stable evidence-access APIs.

- Retrieval Box:
  owns evidence ranking, query interpretation, result selection, and retrieval
  metadata.

- Prompt Builder Box:
  owns final prompt assembly, evidence hierarchy wording, confidence
  instructions, and declared-intent/source-truth framing.

- AI Bridge Box:
  owns model transport, timeouts, malformed response handling, connection
  diagnostics, and model response normalization.

- V10 GUI / Reader Box:
  owns GUI-first workflow, project selection, evidence display, static-context
  inspector, question input/output, and user-facing integration.

- Project Profile Box:
  owns profile detection, fallback, profile metadata, and visible override state.

- Architecture / Governance Box:
  owns canon files, architecture checks, manifest checks, public facade rules,
  layer-boundary rules, and governance tests.

Patch the owner, not the symptom.

Do not modify neighboring boxes unless the task explicitly opens an interop
contract between boxes.

[ENFORCEMENT v1.5.1]
If a proposed change touches files belonging to more than one box, it must be
explicitly justified as an interop contract task. A bundle that silently edits
multiple boxes without declaring the interop contract is a governance violation,
regardless of whether the GUI result looks correct.

4. ARCHITECTURE DOCUMENTATION RULE
----------------------------------

Every non-trivial implementation must leave behind enough structure for a future
engineer or AI to understand:

- why the change exists
- which box owns it
- what inputs it accepts
- what output it produces
- what safety boundary it preserves
- what tests prove it
- what remains not implemented
- what risk was controlled
- what would require a future gate
- what evidence layer is affected

This may appear in docstrings, typed contracts, focused tests, architecture
checks, bundle manifests, schema docs, or canon updates after validation.

Do not rely on memory or conversation context as the only documentation.

5. DESIGN AND IMPLEMENTATION RULE
---------------------------------

Design must be modular, traceable, and maintainable.

Use:

- small modules with one responsibility
- explicit public APIs
- dataclasses, TypedDict, Protocol, or typed contracts instead of loose
  dictionaries when possible
- clear adapter boundaries
- no hidden global state mutation
- no circular imports
- no runtime-heavy imports in pure contract/data modules
- no duplicate retrieval logic
- no duplicate prompt-building logic
- no duplicate schema-loading logic
- no duplicate project-root handling
- no GUI code owning static collection
- no static collector code owning runtime instrumentation
- no runtime collector code owning static schema parsing
- no prompt builder walking the filesystem directly
- no AI bridge choosing evidence ranking
- no support tool owning V10 product behavior

For Reasoner, implementation must always respect:

User-selected PROJECT_ROOT
-> static collector output and/or runtime trace output
-> index loader/schema adapter
-> retriever
-> prompt builder
-> AI bridge
-> GUI answer/evidence display

Never bypass the evidence pipeline with ad-hoc prompt strings or unsupported AI
claims.

6. DETERMINISTIC EVIDENCE PIPELINE RULE
---------------------------------------

Every evidence-affecting operation must declare:

- inputs
- parameters
- preconditions
- output
- failure behavior
- whether it changes source evidence, generated evidence, runtime evidence,
  GUI state, or prompt/model behavior
- provenance/receipt information when relevant

This applies to:

- static collection
- runtime collection
- JSON split/reassembly
- source excerpt extraction
- schema loading
- index building
- retrieval ranking
- project profile detection
- prompt assembly
- AI bridge transport
- GUI evidence display
- generated reports or summaries

The evidence pipeline must remain deterministic.

Correct pattern:

PROJECT_ROOT
-> static collector / runtime collector
-> generated evidence with provenance
-> schema-aware index loader
-> retriever evidence bundle
-> prompt builder
-> AI bridge
-> GUI answer with uncertainty/evidence boundaries

Forbidden pattern:

unseen project assumption
-> ad-hoc prompt
-> unsupported AI answer
-> user treats answer as architecture truth

7. PROJECT ROOT AND PATH SAFETY RULE
------------------------------------

Project Reasoner must separate:

- TOOL_ROOT:
  where Project Reasoner lives

- REASONER_ROOT:
  the kanda_reasoner_app package

- PROJECT_ROOT:
  the user-selected project being analyzed

- OUTPUT_ROOT:
  generated evidence/cache/output location

No production source module may hardcode a specific analyzed project path as
canonical truth.

Rules:

- `E:\eeg_kernel_ai_neural_data_analysis` may appear in tests, smoke helpers,
  preferences, or examples only when explicitly intended.
- Production logic must accept PROJECT_ROOT dynamically.
- Generated JSON must record what project root it came from.
- GUI must make the selected/analyzed project clear to the user.
- Tests must distinguish tool path from analyzed-project path.
- No support tool may silently redefine PROJECT_ROOT for the V10 GUI product.

8. SCHEMA AND GENERATED EVIDENCE SAFETY RULE
--------------------------------------------

Reasoner produces and consumes large generated JSON evidence.

Schema safety is high risk.

Every schema-affecting change must declare:

- old schema shape
- new schema shape
- required sections
- optional sections
- compatibility behavior
- migration strategy
- index loader impact
- retrieval impact
- prompt builder impact
- GUI inspector impact
- tests proving old and new files load as intended

Missing optional sections should degrade gracefully.

Missing required sections should fail clearly.

Corrupt JSON, truncated chunks, wrong part counts, stale manifests, and
mismatched hashes must be handled with clear user-facing or developer-facing
diagnostics.

[ENFORCEMENT v1.5.1]
Schema, registry, or persistence format changes are HIGH risk regardless of
their apparent simplicity. A one-field schema addition is still a migration.
It must declare: old schema shape, new schema shape, migration strategy,
backward-compatibility decision, and what happens to existing evidence files
that predate the change. No schema change is too small to require this
declaration.

9. RETRIEVAL AND PROMPT SAFETY RULE
-----------------------------------

Retrieval and prompt construction are safety-critical for an AI reasoning tool.

Retrieval must:

- rank evidence deterministically enough to test
- expose why an item was selected when possible
- not hide higher-authority evidence behind weaker documentation
- distinguish source files, runtime traces, generated summaries, and docs
- handle missing sections without crashing
- avoid target-project hardcoding
- avoid duplicate ranking logic outside the retriever

Prompt builder must:

- assemble prompts through the canonical prompt owner
- include evidence hierarchy instructions
- state confidence and uncertainty boundaries
- distinguish declared intent from source truth
- avoid theatrical certainty
- avoid unsupported claims
- not scan files directly when index loader/retriever should provide evidence

AI bridge must:

- handle connection failure
- handle timeout
- handle malformed model response
- handle missing model
- preserve user-visible error clarity
- avoid silently substituting unsupported results

[ENFORCEMENT v1.5.1]
A bundle that changes retrieval, prompt, or AI-bridge behavior and declares only
py_compile as validation is not considered validated. These changes require at
minimum a focused test, fixture prompt build, retrieval ranking check, mocked AI
bridge test, or documented manual GUI evidence-grounding validation.

10. GUI-FIRST WORKFLOW RULE
---------------------------

Reasoner is a GUI-first developer tool.

The primary product path must remain:

choose project
-> run or load analysis
-> inspect static context
-> optionally inspect runtime context
-> ask AI
-> receive grounded answer with evidence boundaries

GUI changes must preserve:

- project selection clarity
- evidence visibility
- failure messages
- user cancellation handling
- responsiveness during long tasks
- thread/process cleanup when relevant
- usable layout from laptop to 4K
- no blocking model calls on the GUI thread unless the existing architecture
  explicitly permits it and the user experience remains safe

CLI scripts, smoke scripts, and support tools may exist, but they are not the
primary product path unless explicitly scoped.

11. TESTING, VERIFICATION, AND VALIDATION RULE
----------------------------------------------

Every focused bundle must define the evidence needed to consider it safe.

Use the strongest available validation:

- py_compile for touched Python files
- focused unit tests for pure logic
- focused pytest for collectors, parsers, retriever, prompt builder, profiles,
  and AI bridge
- integration tests for collector -> JSON -> index loader -> retriever -> prompt
- runtime scenario tests for runtime collector changes
- architecture gates for ownership rules
- import smoke tests for startup risk
- manual GUI validation when behavior is visual
- schema compatibility tests for evidence format changes
- prompt/evidence tests for AI-answer grounding changes

Verification asks:
Did we build the implementation correctly?

Validation asks:
Did we build the correct behavior for the Reasoner workflow?

For evidence-affecting code, tests must prove:

- PROJECT_ROOT remains dynamic
- no production hardcoded target-project truth is introduced
- static/runtime/reader boundaries remain separated
- generated evidence loads correctly
- optional sections degrade safely
- retrieval selects expected evidence for a fixture query
- prompt builder preserves declared-intent vs source-truth boundaries
- AI bridge failures are clear and safe
- GUI remains reachable for user workflow when relevant

12. PROCESS MODEL AND AGILE INCREMENT RULE
------------------------------------------

Reasoner development must be incremental, but not chaotic.

Use small validated increments:

1. define requirement
2. identify owner box
3. design narrow contract
4. implement focused bundle
5. validate locally
6. user validates
7. freeze behavior if appropriate
8. update canon only after validation

Agile does not mean skipping architecture.
Plan-driven does not mean blocking progress.

Use disciplined incremental development:

- small scope
- clear contract
- strong validation
- fast feedback
- no uncontrolled scope expansion
- no broad rewrites unless explicitly scoped

13. DEPENDABILITY, SAFETY, SECURITY, AND PRIVACY RULE
-----------------------------------------------------

Reasoner must be dependable because it reads and summarizes project code and may
handle proprietary or sensitive source.

Dependability means:

- predictable behavior
- safe failure
- recoverability
- auditability
- clear error messages
- no silent evidence corruption
- no unsupported AI certainty
- no hidden project-root mutation
- no invalid schema interpretation
- no unsafe fallback that invents evidence

Security and privacy mean:

- do not leak source code or private paths into logs unnecessarily
- do not create unnecessary external dependencies
- avoid unsafe file operations
- validate input files and metadata
- handle corrupt, missing, empty, or unsupported files safely
- avoid arbitrary code execution during static collection
- keep runtime instrumentation explicit and user-controlled
- never let malformed data crash the GUI without explanation
- do not send project code to external services unless explicitly configured
  and consented by the user

Evidence safety overrides convenience.

14. CONFIGURATION MANAGEMENT RULE
---------------------------------

Every change must be traceable.

For each bundle, record:

- files changed
- reason for change
- affected box
- what changed
- what did not change
- validation commands
- expected outputs
- manual GUI test
- next safe step

Runtime/source bundles must place BUNDLE_MANIFEST files inside `_bundle_temp`
when using chunked update bundles.

Canon/governance updates must include exactly the approved governance files and
must preserve the required folder structure for the current canon workflow.

Do not silently change schemas, registries, dropdown option IDs, prompt IDs,
profile IDs, output filenames, cache locations, or persistence formats without
migration and validation.

15. SOFTWARE EVOLUTION RULE
---------------------------

Reasoner is expected to evolve.

Therefore every implementation must be designed for controlled future change.

Before adding a new feature, ask:

- Does this preserve the existing architecture?
- Does this make future profile/retrieval/runtime-trace work safer or harder?
- Does this introduce duplicate ownership?
- Does this create a hidden dependency?
- Does this require migration?
- Does this weaken a frozen gate?
- Does this affect existing generated evidence files?
- Does this affect startup?
- Does this affect GUI-first workflow?
- Does this affect project-agnostic behavior?
- Does this affect evidence reproducibility?

Evolution must be controlled through focused gates, not broad rewrites.

16. PROJECT MANAGEMENT AND RISK RULE
------------------------------------

Before implementation, classify risk:

- LOW:
  local helper, pure validation, docstring, isolated test, no runtime effect

- MEDIUM:
  bounded retrieval scoring, local GUI rendering, project profile metadata,
  documentation/tooling, test infrastructure

- HIGH:
  collector output schema, index loader compatibility, prompt contract,
  AI bridge behavior, threading/processes, persistence, runtime trace schema,
  cross-module coupling

- CRITICAL:
  app startup, main GUI event loop, global path/root logic, model transport
  architecture, collector-output schema overhaul, broad refactor of canonical
  owners

For each task, identify:

- current box
- risk level
- blast radius
- validation needed
- rollback risk
- frozen behavior that must not regress
- manual test required

Do not combine high-risk schema, prompt, retrieval, AI bridge, and GUI lifecycle
changes in the same bundle unless the user explicitly opens an interop contract
task.

17. REASONER TRACEABILITY RULE
------------------------------

Every AI answer and evidence product should be traceable from:

PROJECT_ROOT
-> source files and/or runtime scenario
-> collector output
-> generated JSON evidence
-> index loader/schema adapter
-> retriever evidence bundle
-> prompt builder
-> AI bridge request/response
-> GUI displayed answer/evidence

If this chain cannot be reconstructed, the feature is not professionally ready.

18. REASONER MODULARITY RULE
----------------------------

Major capability areas must remain independent subboxes.

These areas must each have isolated ownership, validators/tests, and interop
contracts:

- static collection
- runtime collection
- JSON split/reassembly
- index loading/schema adaptation
- retrieval
- prompt building
- AI bridge
- project profiles
- GUI inspector/dialog/main window
- architecture governance
- docstring tooling
- daily refactor summaries

Failure in one subbox must not contaminate unrelated subboxes.

For example:

- runtime trace failure must not corrupt static evidence loading
- AI bridge failure must not erase retrieved evidence
- prompt builder failure must not mutate collector output
- JSON splitter failure must not modify source files
- docstring tool failure must not alter Reasoner V10 prompt behavior

19. VISUALIZATION AND GUI ARCHITECTURE GUIDANCE
-----------------------------------------------

Reasoner GUI should remain professional, modular, and fit for developer
workflows.

Preferred GUI principles:

- PySide6/Qt for primary GUI workflow
- tabs or panels for summary, evidence, packaging metadata, documentation intent,
  source truth, runtime traces, and answer output
- splitters and scroll areas for large evidence views
- non-blocking task execution for long-running collection or model calls
- clear status/progress/error messages
- accessible copy/export paths for evidence and prompts when useful

This is architecture guidance, not permission to redesign working GUI boxes
casually.

GUI changes must preserve:

- responsiveness
- resolution independence
- visible evidence context
- separation from collector internals
- no hidden recomputation outside the intended pipeline
- no hardcoded analyzed project path

20. PRE-IMPLEMENTATION CHECKLIST
--------------------------------

Before code, answer:

- What is the exact requirement?
- What is the evidence-safety constraint?
- What is the current box?
- What files belong to this box?
- Which boxes are forbidden for this task?
- What source files, logs, tests, or export evidence prove current behavior?
- What frozen canon must be preserved?
- What is the narrow implementation product?
- What validation proves correctness?
- What remains explicitly not implemented?
- Does this require user validation before canon update?

[ENFORCEMENT v1.5.1]
Added mandatory gate:

- Is this requirement expressed as a testable condition?
  If not, stop and decompose before proceeding.

- If evidence-affecting: is a schema, retrieval, prompt, runtime trace, or GUI
  evidence validation declared?
  If not, stop and define the validation before proceeding.

- If multi-box: is an interop contract explicitly declared?
  If not, stop and scope the contract before proceeding.

21. DELIVERY CHECKLIST
----------------------

Every delivered source bundle must state:

- Changed box
- Reason
- Changed behavior
- Files updated
- What did not change
- Safety boundaries preserved
- Internal validation
- Commands for user validation
- Manual GUI test when needed
- Next safe step

[ENFORCEMENT v1.5.1]
Added mandatory delivery gate:

- Risk classification: LOW / MEDIUM / HIGH / CRITICAL
- Blast radius: which boxes could be affected by a defect in this bundle
- Regression guard: which previously frozen behaviors were explicitly verified
  as unchanged in this delivery

22. FINAL GOVERNANCE RULE
-------------------------

When in doubt, use the professional engineering hierarchy:

1. Evidence integrity
2. Source-code truth
3. Project-root dynamism and project-agnostic behavior
4. Static/runtime/reader layer separation
5. GUI-first workflow
6. Requirements clarity
7. Architecture ownership
8. Traceability
9. Validation and verification
10. Maintainability and modularity
11. Controlled evolution
12. User-approved canon freeze

Do not optimize for quick AI output or quick visual success at the expense of
evidence correctness, architecture integrity, schema safety, or future
maintainability.
