What runtime_collector has that the data_collector currently lacks

There are three concrete pieces of data the runtime collector captures that have no equivalent anywhere in the data collector's current output:
1. Verified live Qt signal connections — TraceSignalConnection

What runtime_collector captures (at runtime):

    The actual sender type and instance name — not a guess from AST
    The actual receiver type, instance name, and slot name — including dynamic lambdas and partials that are invisible to static analysis
    The exact call stack location where .connect() was called (_caller_location via inspect.stack)
    The receiver object resolved at runtime (_resolve_receiver)

What data_collector/collector_qt.py captures (static AST):

    Only connections that look like something.signal.connect(something_else) in the source text
    Misses all dynamically constructed connections (lambdas, functools.partial, runtime-assembled slot targets)
    Cannot know the actual runtime type of the sender or receiver

Value to the data collector: A new collector_qt_runtime.py could read the runtime_trace.json and produce a qt_live_signal_index — connections that were actually wired at runtime, which would validate and enrich the existing static qt_signal_map. This is particularly valuable for the collector_ui_actions.py output which currently has to guess handler targets.
2. Live UI state snapshots — TraceStateSnapshot + collect_visualizer_state

What runtime_collector captures:

    The actual state of every tracked widget attribute at any point during execution (collect_visualizer_state reads live getattr values)
    Which tab was active (notebook.currentIndex, notebook.tabText)
    Widget enable/disable state, text content, selection state — all at the moment they were captured

What data_collector currently has:

    collector_state.py does static attribute assignment tracking — it knows self.foo = X was written, but not what value foo held at runtime
    collector_state_lifecycle.py knows which symbols are candidates for state, but not their actual runtime values

Value to the data collector: A collector_state_snapshots.py could read snapshots and produce a runtime_state_truth_index — ground-truth widget state at key lifecycle moments. This would significantly sharpen the state_lifecycle and state_mutations outputs, which are currently pure inference.
3. Precise execution trace with call stack — TraceEvent + _build_stack_context

What runtime_collector captures:

    Every trace_event() call records: event_type, source_file, source_symbol, message, tags, payload, plus the full call stack at the moment it fired (_build_stack_context via inspect.stack, merged in by _merge_extra_with_stack)
    trace_error and trace_warning distinguish error paths from normal paths at runtime

What data_collector currently has from runtime_scenarios:

    collector_runtime_scenarios.py reads scenario JSON files but only gets event_type, source_file, source_symbol, message, tags — no call stack
    collector_runtime_feature_attribution.py maps scenario events to features/buckets, but the path resolution is probabilistic

Value to the data collector: The full call stack per event makes source_file → feature attribution deterministic instead of probabilistic. A collector_runtime_trace.py could read runtime_trace.json and produce a runtime_call_stack_index — which files were actually on the stack during each feature-relevant event, replacing the current heuristic token-matching in collector_runtime_feature_attribution.py.
