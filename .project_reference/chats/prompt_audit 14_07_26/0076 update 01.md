$ErrorActionPreference = "Stop"

function Invoke-KandaPython {
    param(
        [Parameter(Mandatory = $true)]
        [string[]]$Arguments
    )

    $PreviousPreference = $ErrorActionPreference
    $HasNativePreference = Test-Path `
        variable:PSNativeCommandUseErrorActionPreference

    if ($HasNativePreference) {
        $PreviousNativePreference = `
            $PSNativeCommandUseErrorActionPreference

        $PSNativeCommandUseErrorActionPreference = $false
    }

    try {
        $ErrorActionPreference = "Continue"
        $Output = @(& python @Arguments 2>&1)
        $ExitCode = $LASTEXITCODE
    }
    finally {
        $ErrorActionPreference = $PreviousPreference

        if ($HasNativePreference) {
            $PSNativeCommandUseErrorActionPreference = `
                $PreviousNativePreference
        }
    }

    return [PSCustomObject]@{
        Output = @($Output)
        ExitCode = $ExitCode
    }
}

is it necessary to split prompts to make each one with just one mission or not?

Não é necessário dividir cada prompt até ele executar apenas uma ação microscópica.

O objetivo correto é:

um prompt = uma responsabilidade canônica coerente, com um proprietário claro, limites definidos e um resultado principal.

Um prompt pode conter várias etapas internas quando todas servem à mesma missão. Por exemplo, um prompt de auditoria pode:

    identificar sobreposição;

    verificar metadados;

    comparar rotas;

    produzir recomendações.

Isso continua sendo uma única missão: auditar sem modificar.
Quando dividir um prompt

A divisão é indicada quando o mesmo prompt:

    toma decisões pertencentes a proprietários diferentes;

    audita e também modifica arquivos;

    define identidade e também executa registro ou instalação;

    mistura regra global com regra específica de projeto;

    possui partes que precisam ser chamadas separadamente;

    tem entradas, saídas ou permissões muito diferentes;

    pode mudar uma parte sem que a outra precise mudar;

    está virando um “mega-prompt” que coordena todo o sistema;

    apresenta responsabilidades duplicadas com outros prompts;

    ultrapassa um tamanho em que a lógica deixa de ser facilmente compreensível e validável.

Nesses casos, cada responsabilidade deve ter um proprietário próprio e a integração deve ocorrer por contratos explícitos.
Quando não dividir

Não se deve dividir apenas porque o prompt possui várias seções ou etapas.

A divisão pode ser prejudicial quando gera:

    dezenas de prompts muito pequenos;

    roteamento excessivamente complexo;

    dependências circulares;

    repetição de contexto;

    múltiplos prompts que precisam sempre ser carregados juntos;

    dificuldade para descobrir qual prompt é o verdadeiro proprietário;

    uma nova camada de coordenação apenas para recompor o que foi fragmentado.

Isso seria fragmentação artificial, não melhoria arquitetural.
Modelo ideal para o KANDA Reasoner

Cada prompt deve declarar claramente:

    missão principal;

    autoridade que possui;

    ações que pode executar;

    ações que não pode executar;

    entradas necessárias;

    saída esperada;

    próximo proprietário na sequência;

    condições de bloqueio;

    relação com prompts próximos.

A regra prática é:

    Se duas partes podem ser acionadas, versionadas, validadas ou autorizadas independentemente, provavelmente devem ser prompts diferentes.

    Se duas partes sempre trabalham juntas para produzir um único resultado e compartilham a mesma autoridade, normalmente devem permanecer no mesmo prompt.

A Classe 07 agora está corretamente dividida

A implementação congelada já estabelece uma separação adequada:

    prompt_audit_canon: auditoria somente leitura;

    prompt_canon_reconciliation_protocol: decisão de ciclo de vida, sem escrita;

    project_specific_prompt_generalization: abstração e generalização;

    prompt_identity_code_registry_canon: identidade e códigos;

    prompt_insertion_and_router_registration_protocol: mutação e registro autorizados.

Também proíbe transformar esses estágios em um novo mega-protocolo ou sistema de coordenação.

Essa é uma boa granularidade: cada prompt tem uma autoridade diferente e pode ser validado separadamente, mas eles ainda formam um fluxo coerente.
Decisão para os prompts restantes

Durante a atualização dos 119 prompts, não devemos aplicar uma regra automática de “uma função por prompt”. Para cada auditoria, a decisão deve ser:

    KEEP: responsabilidade já coesa;

    REFACTOR_IN_PLACE: mesma missão, mas com conteúdo confuso ou duplicado;

    SPLIT: existem duas ou mais responsabilidades independentes;

    MERGE: dois prompts possuem a mesma responsabilidade;

    CONVERT_TO_ADAPTER: um prompt antigo precisa apenas encaminhar ao proprietário canônico;

    DEPRECATE: responsabilidade já está integralmente coberta por outro proprietário.

Portanto, alguns prompts precisarão ser divididos, mas a maioria provavelmente deve ser corrigida internamente, consolidada ou reduzida, sem criar uma biblioteca excessivamente fragmentada.

function Invoke-KandaPython {
    param(
        [Parameter(Mandatory = $true)]
        [string[]]$Arguments
    )

    $PreviousPreference = $ErrorActionPreference

    $HasNativePreference = Test-Path `
        variable:PSNativeCommandUseErrorActionPreference

    if ($HasNativePreference) {
        $PreviousNativePreference = `
            $PSNativeCommandUseErrorActionPreference

        $PSNativeCommandUseErrorActionPreference = $false
    }

    try {
        $ErrorActionPreference = "Continue"
        $Output = @(& python @Arguments 2>&1)
        $ExitCode = $LASTEXITCODE
    }
    finally {
        $ErrorActionPreference = $PreviousPreference

        if ($HasNativePreference) {
            $PSNativeCommandUseErrorActionPreference = `
                $PreviousNativePreference
        }
    }

    return [PSCustomObject]@{
        Output = @($Output)
        ExitCode = $ExitCode
    }
}

function Invoke-KandaPython {
    param(
        [Parameter(Mandatory = $true)]
        [string[]]$Arguments
    )

    $PreviousPreference = $ErrorActionPreference

    $HasNativePreference = Test-Path `
        variable:PSNativeCommandUseErrorActionPreference

    if ($HasNativePreference) {
        $PreviousNativePreference = `
            $PSNativeCommandUseErrorActionPreference

        $PSNativeCommandUseErrorActionPreference = $false
    }

    try {
        $ErrorActionPreference = "Continue"
        $Output = @(& python @Arguments 2>&1)
        $ExitCode = $LASTEXITCODE
    }
    finally {
        $ErrorActionPreference = $PreviousPreference

        if ($HasNativePreference) {
            $PSNativeCommandUseErrorActionPreference = `
                $PreviousNativePreference
        }
    }

    return [PSCustomObject]@{
        Output = @($Output)
        ExitCode = $ExitCode
    }
}

    try {
        $ErrorActionPreference = "Continue"
        $Output = @(& python @Arguments 2>&1)
        $ExitCode = $LASTEXITCODE

    }

    return [PSCustomObject]@{

        ExitCode = $ExitCode
    }
}
