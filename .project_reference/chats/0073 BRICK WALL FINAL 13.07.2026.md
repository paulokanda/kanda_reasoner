Concrete defect found in the existing Symbol Indexer

The current implementation identifies a method by checking whether the parent scope name starts with an uppercase letter.

Conceptually, it does this:

if parent[:1].isupper():
    return "method"

That is not structurally valid Python analysis.

I ran the current code against a small fixture and obtained:

class lower:
    def method(self):
        ...

Result:

method -> nested_function

And:

def Outer():
    def Inner():
        ...

Result:

Inner -> method

The scope stack needs to retain scope kinds, such as:

("class", "MyClass")
("function", "outer")

It must not infer ownership from capitalization.

Contract-level contradictions
1. Independent engines versus shared AST reuse

The canon requires one file walk and one AST parse per scan run, reused across engines.

But the proposed interface is:

engine.run_scan(project_root, context_filter=None, options=None)

That encourages every engine to walk and parse the project independently.

A shared-scan architecture requires something closer to:

@dataclass(frozen=True)
class ProjectScanSnapshot:
    project_root: Path
    selected_files: tuple[Path, ...]
    source_by_path: Mapping[str, str]
    ast_by_path: Mapping[str, ast.AST]
    parse_failures: tuple[ParseFailure, ...]
    exclusion_snapshot: ExclusionSnapshot

Engines should consume an immutable scan snapshot:

engine.analyze(snapshot, options)

The shared scanner or coordinator—not every engine—should own traversal and parsing.
2. Universal base class is premature

BaseIntelligenceEngine forces inheritance on systems that already have functional public APIs.

For example, existing Symbol Atlas uses functions and typed option/report objects. Engineering Safety also uses functions and dataclasses.

A structural Protocol or adapter interface would be safer than requiring every current box to inherit from one abstract base class.
3. “Deterministic” needs a clearer definition

Current reports include timestamps, and some existing report systems generate UUID-based identifiers.

Therefore, the canon should distinguish:

Deterministic findings:
Same source and options produce the same findings.

Byte-identical report:
Same source and options produce identical serialized bytes.

The first is required. The second is not currently guaranteed.
4. Storage policy conflict

The canon sends generated reports to:

<project>_delete_after_daily_work\intelligence\

and treats that as the default report location.

That is suitable for disposable interactive scans.

It is not suitable for:

    successful validation evidence;

    durable AI handoff reports;

    accepted architecture evidence;

    reports referenced by future sessions.

The corrected rule should be:

Ephemeral interactive reports:
<project>_delete_after_daily_work\intelligence\

Durable project-specific reports selected for future use:
<project>_show_project_to_AI\project_intelligence\

Canonical source:
Never generated automatically from a report.

5. Hardcoded Error Memory lesson IDs are stale

The implementation roadmap predicts these lessons:

lesson-delete-after-daily-work-bridge-enforcement-v1
lesson-no-isolated-zip-delivery-contract-v1
lesson-validation-output-status-in-sync-required-v1

Those IDs are not present in the current compact Error Memory export. The current export contains ten different active lessons.

The roadmap should not hardcode expected lesson IDs. It should say:

Match the current compact Error Memory dynamically and report exact, partial,
weak, or no match.

6. Patch contents are declared too early

The roadmap predeclares the exact ZIP name and file list before the source audit has selected ownership.

Because the current source already contains all proposed files—and additional later-phase files—the future patch will not be a creation patch.

Its contents must be derived only after:

    current source hashes are checked;

    owner boxes are chosen;

    existing public exports are reviewed;

    validators are selected;

    the current ZIP contract is inspected.

in plain english what features this updated offers

In plain English, the updated Project Intelligence system would make KANDA Reasoner understand the project better, warn about risky changes, and explain what should be checked before an AI edits the code.
What the first updated version would actually add

The first update would mostly work behind the scenes. It would not add a new tab or dramatically change the interface.

It would:

    Create a reliable map of the project

    KANDA would identify:

        files;

        classes;

        functions;

        methods;

        nested functions;

        imports;

        missing docstrings;

        source-code locations.

    In practice, it could say:

        “This project contains 312 functions, 58 classes, and 421 imports. These files appear to own this feature.”

    Improve how KANDA understands code ownership

    It would help answer questions such as:

        Which file owns this feature?

        Where is this function defined?

        Which modules depend on this file?

        Is this button connected to the expected function?

        Which other files may be affected by changing this module?

    Correct and consolidate existing intelligence tools

    The project already has some overlapping scanners. The updated approach would prevent three different systems from independently analyzing the same code.

    Instead, KANDA would have clearer ownership:

        Symbol Atlas handles symbols and relationships.

        Engineering Safety handles risks.

        Architecture Review handles architecture.

        Workflow Review handles GUI and workflow behavior.

        Project Intelligence connects and explains those results.

    Produce clearer reports

    Reports would explain:

        what was found;

        why it matters;

        what should be inspected next;

        what the AI must not assume.

    This is especially useful for a non-programmer directing AI-assisted development.

    Remain read-only and safe

    The scanner would not modify the project, write freeze memory, edit Error Memory, or automatically change files.

    It would inspect and advise only. The first implementation is specifically designed without GUI changes, AI calls, or automatic writes.

Features planned after the foundation is stable
Check patch safety

Before a patch is created, KANDA could examine the files involved and warn:

    “This modifies startup behavior.”

    “This touches freeze-memory logic.”

    “This changes a GUI workflow.”

    “This modifies installation or ZIP handling.”

    “This file has caused a previous regression.”

This is the proposed Risk Change Radar.
Audit GUI tabs

KANDA could inspect a tab and identify:

    buttons shown to the user;

    which function each button calls;

    missing callback functions;

    write actions without an obvious confirmation step;

    labels claiming a feature exists when the implementation may be missing;

    possible differences between the visible interface and the actual workflow.

This would appear inside Workflow Review rather than as another top-level tab.
Find repeated mistake risks

KANDA could compare the current patch with Error Memory and report:

    “This change resembles a previous error involving Windows paths.”

or:

    “This validator may repeat a previously recorded import mistake.”

It would only read Error Memory and warn. It would not create or promote lessons automatically.
Suggest the correct validation command

KANDA could inspect the project and recommend:

    which validation script to run;

    why that script is relevant;

    what success marker should appear;

    whether the command is confirmed or merely inferred.

It would never claim the validation passed unless it was actually run.
Check circular imports

KANDA could identify situations such as:

module_a imports module_b
module_b imports module_c
module_c imports module_a

It would show the files and lines involved and explain why the cycle may be dangerous.
Scan for unsafe code operations

It could detect patterns such as:

    eval;

    exec;

    subprocess with shell=True;

    unsafe ZIP extraction;

    path traversal risks;

    broad delete operations;

    hardcoded project paths;

    possible secrets;

    commands assembled from unchecked user input.

This would be advisory and would not automatically block development.
Create a project health summary

Later, KANDA could combine information from:

    Architecture Review;

    Workflow Review;

    Engineering Safety;

    Symbol Atlas;

    Error Memory;

    validation status.

It could then produce a simple summary:

    “The project is generally healthy. The biggest current risk is duplicated ownership between two architecture scanners. The next recommended action is to consolidate symbol indexing.”

Show relationships between project files

A future relationship map could show groups such as:

    GUI files;

    domain logic;

    validation files;

    installation files;

    freeze-memory files;

    prompt-routing files.

This helps the human and AI understand which files “belong together” before making a change.
Draft architecture decision records

After a validated change, KANDA could prepare a draft explaining:

    what decision was made;

    why it was made;

    alternatives considered;

    validation evidence;

    feature or patch ID.

It would still require human preview and confirmation before writing anything.
Suggest stronger tests

For suitable functions, KANDA could suggest test ideas such as:

    inputs should never change the original object;

    output should remain stable when item order changes;

    invalid paths should always be rejected;

    serializing and deserializing should preserve the same data.

It would suggest tests, not automatically add them.
What the updated version would feel like to you

Instead of KANDA merely showing files and running separate tools, it would increasingly behave like this:

    “You want to change this feature. These are the files that appear to own it. These other files depend on it. This area has caused a previous mistake. These are the likely risks. This is the validation that should be run. Here is what the AI still needs to inspect before editing.”

The main benefit is not more tabs. It is better project understanding and safer guidance inside the tabs that already exist. The design specifically favors internal engines and existing-tab integration rather than adding one new tab for every feature.

The important limitation is that the immediate reconciliation update would mainly improve the internal foundation. The more visible features—GUI auditing, patch-risk warnings, validation suggestions, import-cycle detection, and health summaries—would come afterward, once the existing duplicated systems are consolidated.

Sincerely: for coding and project contextualization, KANDA Reasoner probably does not need another major intelligence layer.

It already has the essential pieces:

    structured AI handoff packages;

    source archives;

    file and routing manifests;

    Architecture Review;

    Workflow Review;

    Symbol Atlas;

    Engineering Safety;

    Error Memory;

    Freeze Memory;

    validation state;

    project boundaries and prompt-routing rules.

Together, those already give an AI enough information to understand the project, locate relevant source, identify risks, inspect prior mistakes, respect frozen behavior, and select validation. The proposed intelligence canon itself says new tools must reuse these systems rather than duplicate them.

What KANDA needs now is not more intelligence. It needs better consolidation and reliability.

The highest-value improvements would be:

    Remove duplicated analysis systems.
    Symbol indexing, risk analysis, and report models already overlap in several areas. Adding more engines would increase confusion.

    Make the current handoff easier to consume.
    The AI already receives the information, but it is distributed across several artifacts. A concise task-specific summary could help, but this should be a small adapter—not a new subsystem.

    Improve freshness and provenance.
    Every generated conclusion should clearly say where it came from, when it was generated, and whether exact source inspection is still required.

    Strengthen validation and regression protection.
    Most practical failures are likely to come from stale paths, wrong imports, inconsistent validators, encoding problems, boundary violations, or outdated generated evidence—not from lack of intelligence.

    Improve the human interface.
    A 2D/3D project map may be useful for you to understand the project visually, but it is not required to make the AI code better.

The honest risk now is overengineering KANDA. More scanners, more schemas, more engines, and more reports could make the system harder for both the human and the AI to understand.

The original roadmap says implementation must stop when existing reusable capabilities are found. Since those capabilities already exist, creating another foundation would contradict the roadmap’s own anti-duplication rule.

My recommendation is:

    Freeze development of new “intelligence engines.” Focus on consolidating existing capabilities, removing duplication, improving handoff clarity, and testing whether AI agents consistently choose the correct files, boundaries, and validators.

Only build a new feature after a real failure demonstrates a specific missing capability. At this stage, KANDA appears to need refinement more than expansion.
