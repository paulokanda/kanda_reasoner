KANDA PROFESSIONAL SOFTWARE ENGINEERING GOVERNANCE LAYER
=======================================================

Use this prompt as an additional governance layer for building the KANDA EEG app professionally.

This layer is inspired by Ian Sommerville-style software engineering principles:
requirements engineering, architecture, design and implementation discipline,
testing, software processes, agile and incremental development, dependability,
safety, security, configuration management, software evolution, quality
management, risk management, project planning, and maintainability.

This layer does not replace the existing KANDA canon.

It must be applied together with the frozen KANDA rules:

- Protect RawCanonical.
- Treat RawDerived as disposable.
- Apply reference before montage.
- Separate physical source identity from active reference transform.
- Separate montage identity from montage execution.
- Preserve clinical EEG meaning.
- Fail safely.
- Use one box per responsibility.
- Deliver one focused bundle per concern.
- Validate before freezing.
- Do not update canon until user validation.

PURPOSE
-------

The KANDA app is clinical EEG software, not only a graphical or data-processing app.

Every implementation decision must be treated as professional software
engineering work with explicit requirements, architecture ownership, traceability,
risk control, validation, maintainability, and controlled evolution.

The goal is to prevent accidental complexity, hidden coupling, unsafe signal
behavior, unvalidated clinical transformations, and regression of previously
validated behavior.

1. REQUIREMENTS ENGINEERING RULE
--------------------------------

Before implementation, define the requirement.

Every task must state:

- User-visible requirement:
  What should the clinician/user be able to do?

- Clinical safety requirement:
  What must never happen to the EEG signal, labels, metadata, or interpretation?

- Functional requirement:
  What specific behavior must the software implement?

- Non-functional requirement:
  What quality must be preserved?
  Examples: safety, reliability, performance, usability, maintainability,
  auditability, portability, Windows/PyCharm compatibility, resolution
  independence.

- Out-of-scope behavior:
  What must not be changed in this bundle?

For KANDA, clinical safety requirements are first-class requirements.
A feature is not complete only because it works visually. It must also preserve
RawCanonical, provenance, label meaning, deterministic rebuild order, and failure
safety.

2. ARCHITECTURE OWNERSHIP RULE
------------------------------

Before editing code, identify the owning architecture box.

Examples:

- Runtime Reference Math Box:
  owns reference math execution and reference-prepared bases.

- Montage Creator Box:
  owns authoring metadata and saved montage definition products.

- Montage Diagnostic Box:
  owns correction and canonization of uncertain labels/reference identity.

- Dropdown Hydration Box:
  owns visible dropdown options and selected UI state.

- Persistence Box:
  owns save/load, schema, migration, and registry integrity.

- Governance Box:
  owns canon rules, validation gates, and frozen decisions.

- Analysis Box:
  owns qEEG, maps, reports, and metrics.

Patch the owner, not the symptom.

Do not modify neighboring boxes unless the task explicitly opens an interop
contract between boxes.

3. ARCHITECTURE DOCUMENTATION RULE
----------------------------------

Every non-trivial implementation must leave behind enough structure for a future
engineer or AI to understand:

- why the change exists
- which box owns it
- what inputs it accepts
- what output it produces
- what safety boundary it preserves
- what tests prove it
- what remains not implemented

This may appear in docstrings, typed contracts, focused tests, architecture
checks, bundle manifests, or canon updates after validation.

Do not rely on memory or conversation context as the only documentation.

4. DESIGN AND IMPLEMENTATION RULE
---------------------------------

Design must be modular, traceable, and maintainable.

Use:

- small modules with one responsibility
- explicit public APIs
- dataclasses or typed contracts instead of loose dictionaries when possible
- clear adapter boundaries
- no hidden global state mutation
- no circular imports
- no runtime-heavy imports in pure contract/data modules
- no duplicate clinical label rules
- no duplicate reference logic
- no UI code owning signal math
- no signal math code owning UI layout

For KANDA, implementation must always respect:

RawCanonical.copy()
-> validated physical/source reference
-> optional active reference transform
-> montage
-> filters/resampling/future signal boxes
-> RawDerived
-> plot/report/analysis consumers

Never use current plot labels or RawDerived as the next computation source.

5. TESTING, VERIFICATION, AND VALIDATION RULE
--------------------------------------------

Every focused bundle must define the evidence needed to consider it safe.

Use the strongest available validation:

- py_compile for touched Python files
- focused unit tests for pure logic
- architecture gates for ownership rules
- focused pytest for behavior
- import smoke tests for startup risk
- manual GUI validation when behavior is visual
- numerical tests for signal math
- provenance/receipt tests for clinical transformations

Verification asks:
Did we build the implementation correctly?

Validation asks:
Did we build the clinically correct behavior for the KANDA workflow?

For signal-affecting code, tests must prove:

- RawCanonical is unchanged
- RawDerived is newly produced
- reference is applied before montage
- no transform is stacked on the plotted signal
- labels remain clinically meaningful
- Fpz is canonical
- FpZ is forbidden
- missing channels fail safely
- previous valid plot is preserved on unsafe/global failure
- provenance or processing receipt reflects the transform

6. PROCESS MODEL AND AGILE INCREMENT RULE
-----------------------------------------

KANDA development must be incremental, but not chaotic.

Use small validated increments:

1. define requirement
2. identify owner box
3. design narrow contract
4. implement focused bundle
5. validate locally
6. user validates
7. freeze behavior if appropriate
8. update canon only after validation

Agile does not mean skipping architecture.
Plan-driven does not mean blocking progress.

Use disciplined incremental development:
small scope, clear contract, strong validation, fast feedback, no uncontrolled
scope expansion.

7. DEPENDABILITY, SAFETY, AND SECURITY RULE
-------------------------------------------

KANDA must be dependable because it handles clinical neurophysiology data.

Dependability means:

- predictable behavior
- safe failure
- recoverability
- auditability
- clear error messages
- no silent data corruption
- no hidden signal mutation
- no invalid clinical label generation
- no unsafe fallback that invents missing evidence

Security and privacy mean:

- do not leak patient data into logs unnecessarily
- do not create unnecessary external dependencies
- avoid unsafe file operations
- validate input files and metadata
- handle corrupt, missing, empty, or unsupported files safely
- never let malformed data crash the clinical workflow without explanation

Clinical safety overrides convenience.

8. CONFIGURATION MANAGEMENT RULE
--------------------------------

Every change must be traceable.

For each bundle, record:

- files changed
- reason for change
- affected box
- what changed
- what did not change
- validation commands
- expected outputs
- manual app test
- next safe step

Runtime/source bundles must place BUNDLE_MANIFEST files inside _bundle_temp.

Canon/governance updates must include exactly the approved governance files and
must preserve the required folder structure for the current canon workflow.

Do not silently change schemas, registries, dropdown option IDs, reference IDs,
or persistence formats without migration and validation.

9. SOFTWARE EVOLUTION RULE
--------------------------

KANDA is expected to evolve.

Therefore every implementation must be designed for controlled future change.

Before adding a new feature, ask:

- Does this preserve the existing architecture?
- Does this make future LAR/CSD/REST/add-back work safer or harder?
- Does this introduce duplicate ownership?
- Does this create a hidden dependency?
- Does this require migration?
- Does this weaken a frozen gate?
- Does this affect saved sessions?
- Does this affect startup?
- Does this affect clinical reproducibility?

Evolution must be controlled through focused gates, not broad rewrites.

10. PROJECT MANAGEMENT AND RISK RULE
------------------------------------

Before implementation, classify risk:

- LOW:
  local helper, pure validation, no runtime effect

- MEDIUM:
  dropdown behavior, persistence metadata, UI lifecycle, test infrastructure

- HIGH:
  RawCanonical/RawDerived behavior, runtime signal execution, reference math,
  montage execution, file import/export, clinical labels, schema migration

High-risk work must be sequential and narrowly gated.

For each task, identify:

- current box
- risk level
- blast radius
- validation needed
- rollback risk
- frozen behavior that must not regress
- manual test required

Do not combine high-risk signal math with UI redesign, persistence migration,
or analysis/report changes in the same bundle unless the user explicitly opens
an interop contract task.

11. KANDA TRACEABILITY RULE
---------------------------

Every clinical transformation must be traceable from:

RawCanonical/base EEG
-> declared physical/source reference identity
-> active reference transform
-> montage definition
-> filters/resampling
-> RawDerived
-> displayed labels
-> analysis/report output

If this chain cannot be reconstructed, the feature is not professionally ready.

12. KANDA MODULARITY RULE
-------------------------

Complex references must remain independent subboxes.

LAR, CSD, REST, and add-back hardware reference must each have:

- isolated module
- validator
- execution adapter
- fail-closed policy
- receipt/fingerprint
- focused tests
- architecture gate
- manual validation guide

Failure in one complex reference must not contaminate simple references or other
complex references.

13. PRE-IMPLEMENTATION CHECKLIST
--------------------------------

Before code, answer:

- What is the exact requirement?
- What is the clinical safety constraint?
- What is the current box?
- What files belong to this box?
- Which boxes are forbidden for this task?
- What source files or logs prove current behavior?
- What frozen canon must be preserved?
- What is the narrow implementation product?
- What validation proves correctness?
- What remains explicitly not implemented?
- Does this require user validation before canon update?

14. DELIVERY CHECKLIST
----------------------

Every delivered source bundle must state:

- Changed box
- Reason
- Changed behavior
- Files updated
- What did not change
- Safety boundaries preserved
- Internal validation
- Commands for user validation
- Manual GUI test when needed
- Next safe step

15. FINAL GOVERNANCE RULE
-------------------------

When in doubt, use the professional engineering hierarchy:

1. Patient/clinical EEG safety
2. RawCanonical protection
3. Deterministic signal pipeline
4. Requirements clarity
5. Architecture ownership
6. Traceability
7. Validation and verification
8. Maintainability and modularity
9. Controlled evolution
10. User-approved canon freeze

Do not optimize for quick visual success at the expense of clinical correctness,
architecture integrity, or future maintainability.
