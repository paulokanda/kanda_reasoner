Method

Build the system around a canonical project knowledge pipeline with four bounded subsystems:
1. Collection subsystem

A desktop runner orchestrates generation of the canonical project index from a chosen project root. This subsystem owns static extraction, symbol/index generation, metadata collection, conflict detection, and final JSON emission. Its primary output is one canonical project JSON artifact. Canonical-conflict logic remains inside this subsystem so duplicate or legacy-equivalent files can be scored and surfaced during collection rather than left for the reasoning layer to guess about later.
2. Runtime evidence subsystem

A separate runtime collector optionally executes scripted or built-in scenarios against the target app, records signal/event behavior, and emits runtime evidence as a secondary artifact. This artifact is linked to the canonical project index by project root, run timestamp, and scenario metadata, but it is not the primary object users load first.
3. Packaging subsystem

A packaging layer handles validation, chunking, and reassembly of the canonical JSON for upload-safe transport. Since the observed payload is already large enough to require many upload-safe parts, chunking should be treated as a first-class post-processing step with deterministic part manifests and stable hashes, not as an afterthought utility.
4. Reasoning and operator UX subsystem

A reasoning UI consumes the canonical index directly, optionally joining runtime evidence when available. The reasoning layer should prefer deterministic retrieval from the canonical index first, then allow model-assisted synthesis on top. Admin tools such as architecture-management and older report compilers should be treated as adjacent operator utilities, not part of the main runtime path.

import contextlib

def _safe_disconnect(signal) -> None:
