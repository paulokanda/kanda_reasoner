## 5. Tool-versus-Project Logic

### 5.1 Core law

Never collapse the reusable Tool into the active target Project.

The Tool performs the operation. The Tool does not automatically become the owner of the Project, its outputs, its durable evidence, or its memories.

### 5.2 Tool-owned capability

The reusable Tool may own:

- GUI tabs and reusable application code;
- analyzers, planners, routers, validators, and refactor engines;
- prompt-library machinery;
- patch-delivery machinery;
- startup-delivery machinery;
- reusable freeze tooling;
- public path resolvers;
- workflow infrastructure;
- reusable transaction and mutation-lane implementation logic.

### 5.3 Active Project-owned truth

The Active Project owns Project-specific truth, including:

- Project source files;
- generated or refactored Project modules;
- generated helper modules;
- Project-specific durable Preview state;
- Project-specific durable Workbench state;
- Project-specific validation evidence;
- Project-specific handoff output;
- Project-specific Error Memory intake;
- Project-specific freeze intake;
- Project-specific frozen memory;
- Project-specific transaction records and receipts.

### 5.4 External Project support root

The external Project support root owns durable Project-support artifacts.

It is not Active Project source.

It is not reusable Tool source.

### 5.5 Transient garbage root

The transient garbage root owns nothing. It is only for:

- disposable staging;
- patch ZIP extraction;
- temporary helpers;
- temporary validation assembly;
- disposable Shadow runs;
- regenerable validation fixtures.

Anything required for correctness after cleanup is forbidden there.

### 5.6 Correct self-hosting rule

Before mutation, ask:

```text
Am I modifying reusable KANDA Reasoner Tool logic,
or am I using the Tool to operate on Active Project source or Project-support state?
```

If the answer is unclear, mutation is blocked.

Hard rules:

- Reusable Tool code must never be installed into Project-support output paths.
- Reusable Tool code must never be installed into transient garbage as its durable owner.
- Project-generated results must not be installed into reusable Tool source merely because KANDA performed the operation.
- Active Project source edits must use the resolved `active_project_root`.
- Durable Project-support writes must use the external `active_project_support_root`.
- Disposable work may use `transient_garbage_root` only.
- A nested `*_show_project_to_AI` folder inside `active_project_root` is forbidden.
- Generated handoff, Preview, validation, report, startup-delivery, or patch artifacts are not automatically source truth.
- Prompt-library canon must be changed in canonical prompt files, not only in generated ZIPs or copied delivery artifacts.
- Self-hosting does not weaken any rule.

When KANDA Reasoner is explicitly selected as both Tool and Active Project, a Tool-owned source change may physically write under the shared root only when:

- the task is explicitly classified as a Tool change;
- the owning Tool box is identified;
- the exact allowed source files are declared;
- the logical Tool/Project distinction remains visible;
- no Project-generated result is misclassified as reusable Tool source;
- no durable Project-support state is written into Tool source;
- Brick Wall authorizes the write.

Physical root equality is not permission to collapse ownership semantics.

## 6. Box Logic

### 6.1 Core law

Every responsibility has one primary owning box.

No implementation may begin until the primary active box is known.

### 6.2 Required box declaration

Before code, state:

- active box;
- responsibility owned by that box;
- owner paths;
- files allowed to change;
- files explicitly out of scope;
- public contract;
- private internals;
- inputs;
- outputs;
- dependencies;
- approved communication routes;
- mutable-state owner;
- fallback behavior;
- cross-box touches;
- validation scope;
- boundary risks.

### 6.3 Box laws

- One box owns one coherent responsibility.
- Public contracts must be small and explicit.
- Private internals must not be imported, called, edited, or mutated by another box.
- Boxes communicate only through approved public contracts, signals, commands, controllers, mediators, adapters, registries, or bridges.
- Every mutable state has exactly one owner.
- Hidden shared globals, silent registries, caches, or singleton state must not become cross-box communication channels.
- A local fix must not expand the active box into a God Box.
- A helper module must not accidentally become the owner of a public facade.
- Cross-box touches must be declared before implementation.
- The active box and every touched external box require focused validation.
- A generated artifact cannot become the public owner of a source contract.

If a task appears to require another box's private internals, stop.

Safe alternatives:

- use the external box's public contract;
- add or improve a governed public contract inside the owner box;
- use an approved adapter, bridge, controller, signal, or mediator;
- separate the work into independently governed owner-box patches.

Do not solve a local problem by contaminating another box.

## 11. Shield Logic

### 11.1 Definition

A KANDA box shield is a tests-first architectural fitness-function suite for one bounded context.

A shield is not:

- a new feature;
- a broad refactor;
- stronger AI or ML;
- a cross-box integration patch;
- an excuse to change another box;
- an automatic authority escalation;
- a substitute for validation;
- a substitute for human freeze confirmation.

### 11.2 What a shield protects

A shield may protect:

- box authority boundary;
- dependency direction;
- truth-source priority;
- public contract;
- side-effect boundary;
- regression-critical outputs;
- do-not-invade-other-box boundary;
- NO_LEAK_LOGIC_V1 boundary;
- no-valid-looking-placeholder behavior;
- state-machine transitions;
- security-sensitive negative cases;
- positive behavior snapshots;
- dependency ceiling.

Master rule:

```text
The machine may suggest.
The canon decides.
The box shield prevents regression.
No other box logic is invaded.
```

### 11.3 Shield trigger

Evaluate a shield after a meaningful box milestone and before broader, stronger, riskier, or cross-box work.

A meaningful milestone may include a new:

- output type;
- caller;
- data source;
- state machine;
- cross-layer interaction;
- Preview or report surface;
- persistence behavior;
- interpretation layer;
- risk boundary;
- authority-like output;
- GUI exposure;
- automation exposure;
- validation behavior;
- freeze behavior;
- startup behavior;
- prompt-routing behavior;
- combined subsystem behavior.

A shield is required only when the canonical owner or current risk analysis requires it. Do not create a shield merely to add more tests or expand scope.

### 11.4 Tests-first workflow

1. Stop feature escalation.
2. Name the shield.
3. Define the owning bounded context.
4. Define protected architecture characteristics.
5. Define the truth-source priority ladder.
6. Define the forbidden authority-escalation matrix.
7. Define the no-valid-looking-placeholder commitment.
8. Define the state machine.
9. Define the positive behavior snapshot.
10. Define the negative regression and security matrix.
11. Define the dependency ceiling.
12. Decide whether a shield card is required.
13. Record the architectural trade-off.
14. Decide whether tests alone are sufficient.
15. Write shield tests.
16. Run tests against current behavior.
17. If tests already pass, do not harden unnecessarily.
18. Add only minimal public-contract hardening when a legal public call can produce forbidden behavior.
19. Validate owning-box tests.
20. Validate relevant adjacent public-contract regressions.
21. Freeze only through explicit human Preview and Confirm and Write.
22. Continue stronger work only after the shield is validated and frozen when freeze is required.

### 11.5 Shield prohibitions

A shield must never:

- invade another box;
- duplicate another box's logic;
- import another box's private internals;
- write another box's memory;
- decide another box's state;
- change another box's authority;
- bypass validation;
- bypass human freeze confirmation;
- mutate startup delivery from an unrelated task;
- mutate prompt-library canon from a non-prompt-library task;
- create durable truth in transient garbage;
- claim advisory output as authoritative;
- introduce stronger ML while pretending to be a shield;
- become a broad cleanup patch;
- produce valid-looking placeholders that hide unavailable authority;
- silently expand the dependency set.

If another box must change, stop and create a separately governed integration patch or owner-box patch.

## 19. Anti-bypass rule

The following never authorize bypassing these gates:

- user urgency;
- a request to "just implement";
- a request to skip routing;
- a request to skip existing prompts;
- physical equality between Tool and Project roots;
- previous familiarity with the feature;
- generated handoff summaries;
- generated startup ZIPs;
- old validation output;
- a previously successful patch;
- an apparently small change;
- an assumption that only one file will be touched;
- a frozen entry with contradictory pending-language evidence;
- a request to freeze automatically;
- a request to memorize Error Memory automatically.

When a contradiction appears:

1. Stop.
2. State the contradiction.
3. Reset affected evidence-sensitive gates.
4. Compare canonical prompt owners.
5. Inspect exact current source.
6. Inspect current public contracts.
7. Inspect manifests, metadata, and validators.
8. Review current compact Error Memory.
9. Review current freeze context.
10. Compare the current handoff.
11. Prefer exact current source for implementation truth.
12. Treat Error Memory as prevention guidance, not source truth.
13. Treat generated artifacts as non-authoritative unless a canon explicitly gives them authority.
14. Take only a read-only safe action until the contradiction is resolved.
