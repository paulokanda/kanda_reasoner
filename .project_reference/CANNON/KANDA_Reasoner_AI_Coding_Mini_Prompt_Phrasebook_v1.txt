KANDA REASONER AI CODING MINI-PROMPT PHRASEBOOK v1

Purpose
Use these phrases while programming with AI and KANDA Reasoner. They are generalized for any Active Project selected in the reusable KANDA Reasoner Tool.

Core identity
- KANDA Reasoner Tool = reusable engineering tool.
- Active Project = selected source and durable-result owner.
- Tool and Project remain logically separate even when both point to the same physical root during self-hosting.
- Brick Wall is the final coding and release authority coordinator.
- Specialist prompts remain authoritative for their own domains.

Placeholders
<active_project> = currently selected Project
<active_project_root> = current Project source root
<active_project_support_root> = current sibling support root
<target> = module, feature, workflow, prompt, or artifact being changed
<primary_box> = Box that owns the main responsibility
<public_facade> = supported public contract of the owning Box
<feature_id> = current immutable feature or repair identity
<operation_id> = current operation identity
<validation_marker> = exact expected validation marker

======================================================================
A. UNIVERSAL PREFIXES
======================================================================

A1. Full universal implementation prefix
Treat KANDA Reasoner as the reusable Tool and <active_project> as the Active Project. Preserve Tool-versus-Project separation even during self-hosting. Route this task through the current prompt indexes, load only the smallest applicable specialist prompt set, apply Box Architecture and NO_LEAK logic, and use Brick Wall as the final coding authority. Inspect exact current source before proposing code. Prefer the smallest verified intervention, preserve public contracts and single-state ownership, validate from current source, and do not claim installation, validation, Freeze, or Error Memory completion without observed evidence.

A2. Short universal guard
Respect Tool/Project boundaries, Box ownership, public-contract-only communication, NO_LEAK logic, current exact source, and Brick Wall authorization. Make the smallest bounded change and preserve all unrelated behavior.

A3. Surgical repair prefix
This is a surgical repair of <target>. Identify the verified defect, its canonical owner, public contract, consumers, and regression risk. Change only the smallest authorized file set inside the owning Box. Keep unrelated corrected behavior shielded and unchanged.

A4. Read-only audit prefix
Audit only. Inspect current Project source and relevant KANDA prompts, but do not modify source, generate an installable patch, write Project memory, or claim validation. Separate findings, evidence, assumptions, and unresolved questions.

A5. Quality-over-growth prefix
Do not create a new engine, scanner, registry, schema, report owner, or context system merely because it sounds useful. First prove a concrete inadequacy in the current canonical capability. Prefer repair, consolidation, or no change.

B. IMPROVED VERSIONS OF COMMON USER PHRASES
======================================================================

B1. Instead of: "Remember to respect box logic."
Use: Apply the Box Architecture Canon. Identify the primary Box, public facade, private internals, state owner, allowed files, declared supporting touches, out-of-scope files, cross-Box contracts, and focused boundary validators before coding.

B2. Instead of: "Use Brick Wall."
Use: Invoke Brick Wall KPR-03-001 now. Show the live Q01-Q40 ledger, current blockers, next safe action, and authorization status. Do not begin with implementation code.

B3. Instead of: "M-card logic is necessary here."
Use: Evaluate MCard applicability under KPR-12-005. Treat KANDA Reasoner as the reusable card machine, <active_project> as the card owner, and <target> as the inserted card. Bind all work to current Project, target, freshness, generation, operation, authorization, and transaction identity. Preserve Project results and eject only target-specific Tool state after verified completion or rollback.

B4. Instead of: "Use exactly the prompt uploaded."
Use: Route to the canonical prompt by exact prompt_id, prompt_code, or prompt_path and apply its current text directly. Do not paraphrase, substitute, merge, or rely on a remembered version when exact prompt content is available.

B5. Instead of: "Search in prompt library for the correct prompt."
Use: Use startup routing first to identify the smallest applicable prompt group, folder card, and specialist prompt path. Open only those canonical prompt-library files. Check duplicates, overlap, owner conflicts, and required companions before applying them.

B6. Instead of: "This is canonical."
Use: Treat this as a proposed canon until current source, owner, consumers, validators, metadata, routing, and conflicts are audited. It becomes authoritative only after governed validation and explicit Freeze confirmation. Do not override an existing frozen owner silently.

B7. Instead of: "Do not mess with the rest of the code."
Use: Preserve every unrelated public contract and validated behavior. Declare the exact changed-file set and files explicitly out of scope. Reject opportunistic cleanup, formatting churn, renaming, or dependency changes outside the verified repair boundary.

B8. Instead of: "Do not let code leak."
Use: Apply NO_LEAK classification. Block wrong-root writes, Tool/Project leakage, cross-Box private reach-in, hidden mutable-state ownership, public API ownership leakage, generated-artifact-as-source authority, and validation or Freeze evidence leakage.

B9. Instead of: "Check the real code; do not guess."
Use: Inspect exact current source, imports, exports, consumers, state owners, current validators, and source fingerprints. Label unsupported conclusions as unresolved. Do not infer runtime success or current behavior from handoff text, memory, filenames, or generated artifacts alone.

B10. Instead of: "Make it SOLID and DRY."
Use: Preserve one cohesive responsibility per owner, stable dependency direction, explicit public contracts, and one authoritative implementation per behavior. Do not create abstraction, helper fragmentation, or indirection unless it removes verified duplication or ownership confusion.

B11. Instead of: "Protect this feature."
Use: Run a Shield Applicability Decision. Strengthen or create focused regression fitness functions only for proven authority, state, boundary, stale-result, path, concurrency, fallback, or high-impact contract risk. Reuse existing tests when sufficient.

B12. Instead of: "Go step by step."
Use: Work through explicit evidence checkpoints: verified problem, Error Memory, exact source, Tool/Project identity, Box boundary, public contracts, state ownership, implementation plan, sandbox validation, patch contract, user-local validation, Freeze, and handoff. Do not advance past a blocked checkpoint.

======================================================================

D1. Prove the problem before implementation. Show concrete evidence, practical impact, current owner inspected, and why the current capability is inadequate.

D2. Search for disconfirming evidence that the current system may already solve this problem.

D3. Classify the change as NEW_FEATURE, REPAIR_EXISTING, CONSOLIDATE, VALIDATOR_ONLY, or NO_CHANGE.

D4. Prefer the smallest adequate intervention that yields a measurable reliability, correctness, safety, usability, or performance gain.

D5. Do not expand scope to unrelated debt. Record unrelated findings separately.

D6. Define the exact target and exact non-targets before editing.

D7. Use one primary Box per governed release. Declare every supporting touch and why it is necessary.

D8. Limit the patch to one coherent behavior or, when explicitly justified, no more than two tightly related implementation islands.

D9. Do not bundle refactoring, feature expansion, GUI redesign, prompt changes, and storage migration into one vague patch.

D10. Identify the stopping condition before implementation. Stop when the named objective is met.

D11. State the rollback boundary before changing source.

D12. Reject the task as BLOCKED when ownership, exact source, current Project identity, or validation evidence is unresolved.

D13. Use NO_CHANGE when the existing implementation is already adequate.

D14. Do not optimize without a named workload, current baseline, and correctness guard.

R. COMPOSITE MINI-PROMPT RECIPES
======================================================================

R1. Safe bug repair
Treat this as a user-detected repair of <target>. Invoke Brick Wall, read compact Error Memory, inspect exact current owner source and consumers, resolve Tool/Project identity, run a Box Boundary Audit, and identify the smallest repair. Preserve unrelated behavior, add focused regression protection, validate on current source, and prepare one governed patch with separate install, validate, Freeze, and Error Memory phases. Do not claim completion without observed evidence.

R2. Safe feature implementation
Before implementing <target>, prove a verified capability gap and search for existing owners to avoid duplication. Resolve the Active Project, select one primary Box, define the public contract and single state owner, compare bounded options when necessary, and obtain Brick Wall authorization. Implement the smallest cohesive feature, validate positive and negative behavior, and deliver through the governed release lifecycle.

R3. Safe refactor
Classify this as behavior-preserving refactoring, inspect exact source and consumers, define the public contract and rollback boundary, and route to the Large Module Refactor Protocol if any touched module is or would exceed 500 lines. Split by cohesive responsibility, preserve imports and behavior, avoid micro-modules, validate consumers and exact rollback, and Freeze each bounded refactor slice before continuing.

R4. GUI correction
Audit the real current GUI implementation and owner contracts before changing it. Keep GUI code responsible for user intent and presentation only; preserve domain ownership, Project selection authority, state reset, failure-mode handling, stale-result rejection, and laptop-to-4K usability. Add real Qt validation when signal delivery, thread affinity, visibility, clicks, or teardown are material.

R5. Prompt-library change
Route this as governed prompt-authoring work. Audit existing prompts, aliases, metadata, routing indexes, folder card, duplicates, overlap, ownership, and create-versus-update-versus-register options. Apply project-specific generalization, preserve exact prompt identity and required companions, validate human and machine routing, and do not edit generated startup copies as canonical source.

R6. Patch delivery
Treat this delivery as a governed release event. Use the exact final ZIP, enforce the declared member set and hashes, stage it under the Active Project daily-work root, install transactionally, validate current installed source, merge Freeze evidence only after validation, and handle Error Memory only for actual reusable failure evidence. Never emit an isolated ZIP.

R7. Freeze continuation
Use the current validated feature identity and local evidence. Confirm that validation_evidence_summary contains the exact literal feature marker and STATUS: IN_SYNC when required.
