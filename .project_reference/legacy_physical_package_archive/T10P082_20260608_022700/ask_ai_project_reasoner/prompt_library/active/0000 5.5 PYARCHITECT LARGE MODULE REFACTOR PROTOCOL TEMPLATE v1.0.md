# 0000 5.5 PYARCHITECT LARGE MODULE REFACTOR PROTOCOL TEMPLATE v1.0

Version: 1.0.0
Status: Reusable large-module refactor protocol
Use: Load only when a file is above 500 lines, when the user requests refactoring, or when helper splitting is required.

## Purpose

Safely split large modules into a thin public entry file plus responsibility-specific helper files without changing public API or breaking behavior.


## Project-Agnostic Contract

This prompt must work for any software project. Replace variables before use.

Required variables:

```text
<PROJECT_ROOT>
<PROJECT_NAME>
<PRODUCT_PACKAGE>
<TASK_DESCRIPTION>
<TASK_SLUG>
<GOVERNANCE_FOLDER>
<VALIDATION_COMMANDS>
<OUTPUT_FOLDER>
<SOURCE_FILES>
<LOG_FILES>
```

Rules:
- Do not hardcode one project root.
- Do not assume one product package.
- Do not treat examples as active project truth.
- Use current source files, logs, and validation output as evidence.
- If evidence is missing, request it before implementation.

## Approval Gates

Task 0: audit only, then stop for approval.
Task 1: roadmap and decomposition only, then stop for approval.
Task 2: implementation only after approval.

## Task 0 Audit

Report line count, public symbols, imports, classes/functions, responsibilities, risks, tests available, helper split candidates, owner box, in-scope behavior, out-of-scope behavior, and blind spots.

## Task 1 Roadmap

Define helper folder, helper files, purpose of each helper, symbols moved, dependencies, public API preservation, validation plan, rollback plan, and expected line counts.

## Task 2 Implementation

Move logic by responsibility. Preserve public API. Avoid circular imports. Avoid catch-all helpers. Do not mix behavior changes into refactor.

## Final Rule

Do not refactor to look organized while changing behavior accidentally.
